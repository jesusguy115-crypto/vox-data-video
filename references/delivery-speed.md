# 整轮交付与维护分开

用户要求缩短的是从提出任务到拿到可播放视频的等待时间。机器编码、整个自动脚本、人工核对、模型准备和对话等待分别记录；不能把“编码3秒”说成“整轮3秒”。没有证据不承诺固定交付分钟数。

## 普通制作

接收表格 → 一次提供主题/单位/配色入口 → 核对数据及选图 → 调用固定入口 → 看一次关键帧与解码结果 → 立即交付 MP4。

资料已研究且模板支持时，不重读全部参考、不重新浏览风格、不重写模板。标题和配色回答已在会话中时直接采用。首次依赖/编译可以缓存，后续任务复用；字体、纸张、文字层和静止尾帧缓存不能改坏视觉质量。优先直接流式编码，避免数百张4K PNG中转。

当最后一项必要用户回答到达后，直接填参数并运行。不要在此阶段加一次风格研究、另起版本或更新 Skill。执行期间给简短的真实进度，不用反复解释相同方案制造额外等待。

只因数据错误、标签遮挡/不可读、无法播放、缺失要求或用户新修改而重渲染；纯粹临时想微调外观不能成为正常出片反复迭代的理由。保留既定视觉质量，不能为了提速偷偷简化纸层、字体或动效。

## 维护

用户要求更新 Skill、修版或研究新方向时，才修改模板并作必要验证。复用已验证版本供后续生产。发布 GitHub需用户明确授权，不能把一次视频请求当作发布授权。

若是新数据结构不受现有模板支持，简短说明需要扩展，仍选正确图形。不能为追求速度把动态圆堆换横条或把组成占比默认换柱状。首次新增图形的开发时间与后续复用时间分开汇报。
